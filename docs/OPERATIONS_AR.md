# تشغيل CyberGuard AI — إصدار هندسي 0.1.0

هذه نسخة تشغيل محلية للوظائف المدرجة هنا، وليست اكتمال منصة الحماية ذات 1,440 متطلبًا. لا توجد كلمة مرور افتراضية ولا بيانات عرض داخل قاعدة التشغيل.

## التشغيل الأول

1. يلزم Node.js 24.21.0 أو إصدار تصحيحي أحدث ضمن 24. لا يلزم `npm install`؛ لا توجد تبعيات تشغيل npm.
2. شغّل `START_CYBERGUARD.cmd` على Windows، أو نفّذ `node scripts/launch.js` من مجلد المشروع.
3. افتح `http://127.0.0.1:4310` على الجهاز نفسه. لا تعرضه عبر tunnel أو reverse proxy؛ النسخة الحالية تقبل loopback فقط.
4. اقرأ ملف `data/setup-token` محليًا وأدخل الرمز في شاشة التهيئة. لا ترسله في محادثة أو تحفظه في لقطة شاشة. اختر اسم مسؤول وكلمة مرور لا تقل عن 14 حرفًا. يُحذف الملف بعد إنشاء أول مسؤول.
5. سجّل الدخول. إنشاء حساب ثانٍ بدور مسؤول يسمح بمراجعة طلبات الموافقات بصورة مستقلة؛ دور المحلل يراجع التنبيهات والتحقيقات، والمشاهد للقراءة فقط.

لا تُفتح نافذة متصفح تلقائيًا ولا يوجد اتصال بخدمة سحابية. `CG_PORT` يغير المنفذ المحلي، و`CG_DATA_DIR` يغير مجلد البيانات. حافظ على المجلد في حساب Windows الخاص بالمشغل وبصلاحيات وصول محدودة. تشفير القرص ونسخ البيانات مسؤولية التشغيل الحالية؛ SQLite ليست مشفرة بواسطة التطبيق.

## إضافة بيانات حقيقية مصرح بها

من «مصادر البيانات» أنشئ مصدرًا، ثم استورد ملف JSON وفق [عقد الأحداث](TELEMETRY_AR.md). المفتاح المستقل يظهر في حقل مخفي مرة واحدة؛ لا تضعه في ملف مواصفات أو command history. يمكن إبطاله أو تدويره من الواجهة. لا يرسل النظام ملفاتك إلى خارج الجهاز.

«جرد هذا الجهاز» عملية صريحة للقراءة فقط: اسم المضيف، عائلة النظام وعناوين الواجهات. لا تجمع المستخدمين أو كلمات المرور أو محتويات الملفات، ولا تفحص الشبكة أو تستنتج نجاح الحماية. تغيير اسم المضيف قد ينتج هوية جديدة؛ لا يعد ذلك محرك ربط هوية كاملًا.

عينات التنزيل و`node scripts/ui-lab.js` **اصطناعية فقط**. المختبر على المنفذ 4311 وبقاعدة مؤقتة، ولا يضيف بيانات إلى التشغيل الحقيقي. لا يُستخدم كخدمة دائمة.

## مسارات العمل المتاحة

- الأصل ← آخر أحداثه وبصماته ← تقرير أدلة JSON محلي حتمي، لا تقرير LLM.
- التنبيه ← إقرار بشري ← فتح تحقيق ← ملاحظات وحالة التحقيق. الإقرار لا يغلق التحقيق تلقائيًا ولا يثبت وصول رسالة SMS/Email.
- الأصل ← معاينة تغيير الأهمية ← موافقة مسؤول آخر ← تنفيذ محلي والتحقق ← تراجع إذا لم تتغير النسخة. لا منفذ جهاز أو firewall أو NCC في هذه النسخة.
- المصدر المتوقف يظهر «فقدان الرؤية» وينتج تنبيه صحة مستقلًا. وصول أحداث قديمة يثبت قناة الاستقبال فقط، ولا يثبت حداثة كل دليل.
- سجل التدقيق ← فحص التسلسل. السلسلة محلية ولا توفر WORM أو حماية من مدير نظام يعيد كتابة قاعدة البيانات كاملة.
- تغطية المتطلبات ← النصوص الأصلية والتصنيف الأولي. العدد 1,440 هو جرد المتطلبات؛ `Verified = 0` يعني أن قبولها الكامل عبر منصاتها لم يثبت بعد.

## إيقاف وحفظ واستعادة قاعدة التشغيل

أوقف الخادم بـCtrl+C وانتظر خروجه قبل نسخ مجلد `data` كاملًا إلى مخزن خاص مشفر. لا تنسخ DB منفردة أثناء التشغيل؛ ملفات WAL قد تحتوي معاملات أحدث. لاستعادة نسخة: أوقف الخدمة، احتفظ بنسخة المجلد الحالي، واستعد المجلد الخاص كاملًا ثم أعد التشغيل وفحص سلسلة التدقيق. هذه إجراءات حفظ قاعدة التطبيق فقط؛ ليست اختبارات استعادة Windows/AD أو دليل RTO/RPO للمؤسسة.

لا توجد أداة استرداد كلمة مرور أو MFA في هذا الإصدار؛ يجب حفظ حسابات المسؤولين في مدير كلمات مرور. لا تعدّل hashes أو قاعدة البيانات يدويًا. لا توجد مهمة تحديث أو تثبيت خدمة Windows أو نشر شبكة تلقائية.

## فحص الإصدار

`node scripts/verify.js` يفحص سلامة المواصفات والصياغة ويشغّل مجموعة الاختبارات، ويحفظ النتائج في `artifacts/verification.json` و`artifacts/tests.tap`. اختبارات الخادم تستخدم قواعد مؤقتة وأحداثًا اصطناعية ولا تُجري فحص شبكة.

راجع [المراحل والعوائق](engineering/MILESTONES_AR.md) و[سجل التحقق](engineering/VALIDATION_AR.md) قبل أي ادعاء تشغيل إنتاجي.

## HTTPS والدخول الموحد والنطاقات (CG-052)

- HTTPS: شغّل بـ`CG_TLS=self-signed` لشهادة محلية تُولَّد في مجلد البيانات (المفتاح بصلاحية المالك فقط ولا يدخل المستودع)، أو بـ`CG_TLS_CERT` و`CG_TLS_KEY` لشهادة المؤسسة. TLS 1.2 فأعلى، مع HSTS وملفات تعريف ارتباط Secure وHttpOnly وSameSite=Strict.
- الدخول الموحد OIDC: من الإعدادات يضبط مسؤول بتحقق MFA حديث المُصدر (HTTPS) ومعرف العميل واسم متغير البيئة الذي يحمل السر (لا يُخزن السر) والمستأجر المسموح، وربط كل مجموعة من مجموعات مزود الهوية بدور ومستأجر ومواقع ومجالات. يُرفض الدخول بلا مطالبة MFA (`amr` أو `acr`)، أو من مستأجر آخر، أو بمجموعة غير مربوطة، أو برمز توقيعه أو جمهوره أو وقته أو nonce غير صحيح، وتُسجل كل حالة رفض في التدقيق.
- النطاق لكل مستخدم: `CG_TENANT` مستأجر هذه النسخة؛ المستخدم المقصور على مواقع (من `asset.context.site`) يرى تنبيهات وأحداث وأصول وحالات وإجراءات مواقعه فقط، ولا يفتح واجهات الوضع على مستوى المؤسسة؛ والمقصور على مجالات (السحابة، الشبكة، الهوية، الاستجابة، الثغرات) لا يفتح غيرها.

## الوصول عن بعد عبر Zero Trust أو VPN وقيود الأجهزة (CG-053)

- الافتراضي: الاستماع على 127.0.0.1 فقط، ولا يُقبل اسم مضيف غير محلي، ولا يُقبل طلب بعنوان محلي من عنوان بعيد.
- Zero Trust: يبقى CyberGuard على 127.0.0.1 ويعمل موصل البوابة (مثل cloudflared أو موصل تطبيق ZTNA) على الجهاز نفسه. اضبط `CG_REMOTE_ACCESS=ztna` و`CG_PUBLIC_HOSTS=soc.example.com` و`CG_ZTNA_ISSUER` و`CG_ZTNA_AUDIENCE` و`CG_ZTNA_JWKS_URL` (HTTPS)، واسم ترويسة التأكيد في `CG_ZTNA_HEADER` (الافتراضي `cf-access-jwt-assertion` لـCloudflare Access). كل طلب للاسم العام يحتاج تأكيدًا موقّعًا صالحًا للجمهور وغير منتهٍ، ويُشترط امتثال الجهاز بـ`CG_ZTNA_DEVICE_CLAIM` و`CG_ZTNA_DEVICE_VALUE` (مثل `device_posture.compliant=true`).
- VPN: `CG_REMOTE_ACCESS=vpn` مع TLS إلزامي و`CG_LISTEN_HOST` عنوان واجهة الـVPN الخاص (لا يُقبل عنوان عام) و`CG_VPN_CIDRS` نطاقات عملاء الـVPN. ومع `CG_TLS_CLIENT_CA` (شهادة جهة إصدار أجهزة المؤسسة) لا يتصل إلا جهاز يحمل شهادة صادرة منها (mTLS).
- كل دخول يُسجل في التدقيق بطريقة الوصول والهوية لدى البوابة والجهاز. والواجهة قابلة للتثبيت كتطبيق على Windows والأجهزة اللوحية والهواتف (Web App Manifest).

## التشغيل على لينكس (Debian/Ubuntu/Kali/RHEL)

- المتطلب: Node.js 24. التثبيت: `sudo sh deploy/linux/install.sh` ينسخ النسخة إلى `/opt/cyberguard` وينشئ مستخدم نظام `cyberguard` ومجلد بيانات `/var/lib/cyberguard` بصلاحية المالك فقط، ويشغّل خدمة systemd مقيدة (`deploy/linux/cyberguard.service`: بلا صلاحيات إضافية، ونظام ملفات للقراءة فقط عدا مجلد البيانات، ومنع الأجهزة والوحدات). الإعدادات في `/etc/cyberguard/cyberguard.env`.
- الاستماع على 127.0.0.1:4310 افتراضيًا، ويُتحقق في CI على Ubuntu حقيقي من تثبيت الخدمة وتشغيلها وعدم الاستماع خارج loopback.
- الفحص التشغيلي الشامل: `node scripts/smoke.js` يشغّل النسخة في مجلد مؤقت ويحمّل بيانات كل الموصلات ويستدعي كل الصفحات وواجهات القراءة ويتحقق من سلسلة التدقيق؛ ويعمل في CI على Windows وUbuntu وmacOS.

## تعدد المستأجرين: العزل والحدود والاحتفاظ (CG-059)

- كل عميل (مستأجر) نسخة CyberGuard مستقلة: قاعدة بيانات ومفتاح مخزن أسرار وسلسلة تدقيق ورمز تهيئة ومستخدمون وجلسات وإعدادات SSO خاصة به، ولا يُشارك شيء بين المستأجرين.
- لينكس: بعد `install.sh` أضف كل مستأجر بـ`sudo sh deploy/linux/add-tenant.sh <tenant-id> <port>`؛ يعمل كخدمة `cyberguard@<tenant-id>` بمستخدم خدمة مؤقت مختلف لكل مستأجر (DynamicUser) ومجلد `/var/lib/cyberguard-tenants/<tenant-id>`، وإعداداته في `/etc/cyberguard/tenants/<tenant-id>.env`. يُرفض المنفذ المستخدم.
- Windows/macOS أو لينكس بلا systemd: `node scripts/tenants.js add <tenant-id> --port <port>` ثم `node scripts/tenants.js run` (عملية مستقلة لكل مستأجر).
- داخل كل نسخة يضبط المسؤول بتحقق MFA حديث من الإعدادات: مدة الاحتفاظ بسجلات النشاط، وحد الأحداث اليومي، وحد المصادر والأصول والتخزين. البيانات التي تتجاوز الحد تُرفض كاملة (لا تُخزن نصف دفعة) مع تنبيه CG-TENANT-LIMIT-059 وسجل تدقيق.
- الاحتفاظ يُطبق كل ساعة ويحذف سجلات النشاط فقط (السجلات، محاولات الدخول، جلسات الوصول عن بعد، الاكتشاف) بعد المدة، وتبقى سجلات الحالة وأدلة التنبيهات المفتوحة وسلسلة التدقيق.

## العمل أثناء الانقطاع والمطابقة بعده (CG-060)

- CyberGuard يعمل محليًا بالكامل ولا يحتاج الإنترنت. المجمعات البعيدة ترسل عبر `node scripts/forwarder.js`: `enqueue <file>` يضع الملف في طابور محلي دائم (`--spool <dir>`)، و`run` يرسل بالترتيب ويعيد المحاولة بتأخير متضاعف مع عشوائية عند انقطاع الشبكة أو الخادم (408/429/5xx)، و`status` يعرض الطابور. رمز المصدر من `CG_SOURCE_TOKEN` فقط.
- إعادة الإرسال آمنة: كل حدث يُخزن مرة واحدة لكل (مصدر، event_id)، والتكرار يُحسب «مكررًا» دون نسخة ثانية. الملف المرفوض لسبب في محتواه يُنقل إلى `rejected` مع السبب.
- يبلغ المرسل الخادم بعمق الطابور وأقدم عنصر؛ تأخر أكثر من ساعة يرفع CG-DELIVERY-BACKLOG-060.
- مهام التنفيذ التي لا يستلمها الموصل خلال 60 دقيقة تنتهي (CG-RESPONSE-STALE-060) وتحتاج طلبًا وموافقة جديدين على الحالة الحالية؛ مهام التراجع لا تنتهي وتنتظر عودة الموصل، ولا يُعد التراجع ناجحًا إلا بحالة مستعادة ودليل من الموصل. صفحة الاستجابة تعرض تقرير المطابقة.

## مراحل التشغيل: مختبر ثم تجربة ثم توسع (CG-062)

- من الإعدادات يطلب مسؤول (MFA حديث) مرحلة ويعتمدها مسؤول آخر. المختبر المعزول يحتاج نطاق أصول أو مواقع المختبر ودليل اختبارات ناجحة للنسخة وسلسلة تدقيق سليمة.
- التجربة المحدودة تحتاج تشغيل تحقق داخل الخطة في بيئة المختبر ونطاقًا صريحًا (حتى 50 أصلًا أو مواقع محددة، بلا `*`) ومرجع تفويض.
- التوسع يحتاج 7 أيام تجربة على الأقل و10 تنبيهات مصنفة بدقة ≥ 0.7 واكتمال تصنيف ≥ 0.8 وفشل استجابة ≤ 0.2 وتغطية أجهزة ≥ 0.9، وكلها مقاسة من بيانات النسخة نفسها.
- أثناء المختبر والتجربة تُرفض إجراءات الاستجابة لأي أصل خارج نطاق المرحلة (`outside_rollout_stage_scope`). الرجوع لمرحلة سابقة لا يحتاج شروطًا لكنه يحتاج موافقة ثانية.

## فحص سطح الهجوم الخارجي لأصولك المصرح بها (CG-072)

- يعمل على لينكس وWindows وmacOS: `node scripts/attack-surface.js token` يولد قيمة تنشرها كسجل DNS TXT `cyberguard-verify=...` لإثبات ملكية النطاق.
- ملف النطاق `scope.json`: مرجع التفويض، والمالك، ونهاية نافذة التفويض، والنطاقات (تحقق DNS أو تصريح بمرجع)، ونطاقات العناوين التي تملكها (حتى /22)، والمنافذ ومعدل الفحص.
- `node scripts/attack-surface.js scan --scope scope.json --output easm.json` يفحص سجلات DNS وSPF/DMARC/CAA، وشهادات TLS (الانتهاء، التوقيع الذاتي، مطابقة الاسم، البروتوكولات القديمة)، والخدمات المكشوفة (خاصة SSH/RDP/SMB/قواعد البيانات)، وترويسة HSTS.
- على لينكس أضف `--nmap` (بعد `sudo apt install nmap`) لكشف إصدارات الخدمات بـnmap، فقط على العناوين داخل نطاقك وبالمعدل المحدد. يُختبر هذا فعليًا في CI على Ubuntu.
- لا يُتصل أبدًا بعنوان خارج النطاقات المصرح بها (يُسجل «لم يُفحص»)، ولا يُستغل شيء ولا تُجرب كلمات مرور. أدخل الملف الناتج إلى CyberGuard فتظهر النتائج في صفحة الثغرات وتُرفع تنبيهات CG-EASM-072 مع طريقة الإصلاح.

## فحص الملفات المشبوهة دون تشغيلها (CG-092)

- `node scripts/file-triage.js scan <ملف>... --rules rules.yar --output triage.json` يحسب البصمات ونوع الملف، ويطابق قواعد YARA (مجموعة مدمجة على كل الأنظمة، أو أداة yara الكاملة على لينكس بـ`--yara` بعد `sudo apt install yara`)، ويفحص توقيع الناشر على Windows، وسمعة البصمة من قوائم محلية معتمدة (`--known-bad` و`--known-good`). لا يُشغَّل أي ملف ولا يُرسل شيء للإنترنت.
- `--quarantine <مجلد> --reason "<السبب>"` ينقل الملفات الخبيثة كما هي باسم بصمتها، للقراءة فقط، مع سجل حيازة مربوط بالبصمات؛ و`verify-custody --quarantine <مجلد>` يتحقق من سلامة السجل والملفات.
- يُختبر في CI على Ubuntu بأداة yara الحقيقية وملف اختبار EICAR القياسي. أدخل الناتج إلى CyberGuard فتظهر النتائج في صفحة التهديدات وترفع CG-FILE-MALICIOUS-092 أو CG-FILE-SUSPICIOUS-092.

## التفجير في مختبر معزول (CG-093)

- غير مفعّل افتراضيًا ولا يعمل تلقائيًا أبدًا. CyberGuard لا يشغّل أي ملف؛ يدير مهام لبيئة تفجير منفصلة (مثل CAPE على جهاز لينكس معزول) يسجلها مسؤول بتحقق MFA حديث مع مصدر من نوع `sandbox-connector` لا يستطيع إرسال بيانات مراقبة.
- يطلب شخص التفجير لملف معزول فقط (CG-092) ويعتمده مسؤول آخر. البيئة ترسل فحص عزل ذاتي (`POST /api/sources/<id>/sandbox/isolation`) يثبت عدم الوصول للإنترنت أو الإنتاج، ولا تُسلَّم المهام إلا إذا نجح خلال 24 ساعة؛ وتُسلَّم البصمة ومرجع الحيازة فقط، والملف يُنقل من العزل بإجراء الحيازة في المختبر.
- التقرير السلوكي يجب أن يطابق البصمة. أي محاولة اتصال غير محظورة أو فشل فحص العزل يوقف البيئة فورًا ويلغي المهام المعتمدة ويرفع CG-SANDBOX-ISOLATION-093 (حرج).

## أمان لينكس (CG-094)

- على كل جهاز لينكس مُدار: `sudo bash scripts/agent/linux-security.sh out.json <مرجع>` (للقراءة فقط). يجمع حالة auditd وعدد قواعده، وقابلية قراءة journald، ودعم eBPF بحسب النواة وBTF مع السبب عند عدم الدعم، وحالة Falco، وبصمات ملفات sudoers وعدد قواعد NOPASSWD ومنح ALL وأعضاء sudo/wheel واستخدام sudo خلال 24 ساعة، وبصمات ملفات cron ووحدات systemd. لا يُنسخ محتوى أي ملف.
- يقارن CyberGuard كل لقطة بالسابقة: إضافة أو تعديل cron/systemd يرفع CG-LINUX-PERSIST-094، وتغيير sudoers أو وجود NOPASSWD يرفع CG-LINUX-SUDO-094، وغياب سجل تدقيق مقروء يرفع CG-LINUX-VISIBILITY-094.
- تنبيهات Falco تُستورد بصيغة `falco-json` عبر `node scripts/logs-to-telemetry.js` وتظهر كأحداث IDS. يُختبر الجمع فعليًا كـroot في CI على Ubuntu مع كشف مهمة cron مضافة.

## تغطية macOS والجوال والأجهزة الشخصية (CG-095)

- يصدّر مسؤول Intune قائمة الأجهزة للقراءة فقط (`GET /deviceManagement/managedDevices` بصلاحية DeviceManagementManagedDevices.Read.All)، ثم: `CG_MDM_SALT=<قيمة سرية> node scripts/mdm-to-telemetry.js managedDevices.json out.json`.
- الأجهزة الشخصية (BYOD) تُحفظ بمرجع مستعار فقط مع وضعها الأمني؛ لا يُحفظ اسم المستخدم ولا الرقم التسلسلي ولا رقم الهاتف ولا IMEI ولا الموقع.
- التنبيهات: كسر حماية/root (مرتفع)، عدم الامتثال، جهاز مؤسسة غير مشفر، انقطاع أكثر من 7 أيام. وتعرض صفحة المصادر ما تراه الإدارة وما لا تراه لكل منصة حتى لا يُعتبر الجوال المُدار مراقبًا بالكامل.

## وضع الشبكة لكل مجال (CG-096)

- من تصدير `show running-config` مصرح به وللقراءة فقط: `node scripts/network-posture.js running-config.txt --device-ref <جهاز> --authorization-ref <مرجع> --output out.json [--sections acl,nat,...]`.
- يقيّم IPv4 وIPv6 (مرشحات وRA Guard) وWi-Fi (شبكات مفتوحة/WPA1) وDNS وDHCP (snooping) وVPN (IKE/ESP ضعيفة) وVLAN 1 ومنافذ Trunk (DTP، كل الشبكات، native VLAN 1) وACL (permit ip any any) وNAT الثابت المكشوف وBGP (مصادقة ومرشحات) وOSPF (مصادقة).
- المجال غير المصدَّر يظهر «لم يُجمع»، والتصدير الذي فيه أخطاء صلاحية يظهر «غير مقروء»؛ ولا يُفترض أن أي منهما آمن. كل ملاحظة ترفع CG-NETPOSTURE-096 مع طريقة الإصلاح.

## مراجعة الجدار الناري والأثر قبل التعديل (CG-097)

- تحليل القواعد يصنف كل قاعدة إلى وارد أو خارج أو داخلي شرق-غرب، ويكشف السماح أي-إلى-أي، والقواعد المظللة أو المتداخلة جزئيًا بإجراء مختلف، والحركة الداخلية المفتوحة بالكامل، ومنافذ الإدارة المفتوحة داخليًا، والحركة الخارجة غير المرشحة.
- قبل أي تعديل: من صفحة نتائج الأمان «احسب الأثر دون تطبيق» (أو `POST /api/firewall-rules/what-if`) لإضافة أو حذف أو تعطيل أو نقل قاعدة؛ يعرض التدفقات التي ستُفتح أو تُغلق والملاحظات الجديدة والتي ستُحل. لا يتغير شيء على الجهاز.

## Zero Trust وNAC (CG-098)

- يصرح كل موقع بسياسة `nac.policy`: طريقة التحقق من المستخدم (EAP-TLS/PEAP/...) ومن الجهاز (شهادة/MAB)، ومصير الأجهزة غير المعروفة، وعزل الضيوف، والأجهزة غير المُدارة، وفحص الوضع، ومدة إعادة التحقق، والتقسيم.
- يقيّم CyberGuard السياسة (درجة من 100 وملاحظات بالعربية) ويقارنها بسجلات FreeRADIUS المستوردة (`node scripts/logs-to-telemetry.js freeradius ...`): إن لم تُرصد أي عملية تحقق لا يُعتبر التطبيق مؤكدًا، وإن نجح دخول بعنوان MAC بينما السياسة تتطلب شهادات يُبلغ عن انحراف. الفجوات المرتفعة ترفع CG-NAC-POLICY-098، وتُعرض المواقع التي بلا سياسة.

## ربط التهديدات الشبكية (CG-099)

- صيغ جديدة: `zeek-ssl` (بيانات TLS الوصفية: اسم الخادم والإصدار) و`squid-access` (الوكيل؛ يُحفظ اسم المضيف فقط دون المسار أو معاملات الاستعلام)، إلى جانب Suricata وZeek conn وسجلات DNS والتدفقات.
- تُربط الإشارات لكل جهاز داخلي خلال 15 دقيقة: تنبيه IDS، أو نطاق يشبه المولّد آليًا، أو حظر الوكيل، أو TLS بلا اسم خادم؛ ولا تُرفع ملاحظة إلا إذا أكدها مصدر مستقل آخر. ثلاثة مصادر فأكثر تعني ثقة عالية. تُرفع CG-NETCORR-099.
- الحدود معروضة: لا يُفك التشفير؛ TLS 1.3 مع ECH يخفي اسم الخادم؛ QUIC وDoH/DoT تتجاوز سجلات DNS والوكيل؛ التدفقات لا تبين المحتوى.

## وضع سلامة أنظمة التشغيل OT/ICS (CG-100)

- سجّل أجهزة التشغيل (PLC وRTU وSCADA/HMI وBMS وأنظمة السلامة والأجهزة الطبية) كأدلة `ot.asset_profile`: الفئة ومستوى Purdue والبروتوكولات وإمكانية الوصول من تقنية المعلومات والوصول عن بعد والمراقبة السلبية والنسخ الاحتياطي لمنطق التحكم.
- القراءة سلبية أولًا: تُرفض خطط التحقق النشطة (غير passive) على أجهزة التشغيل في الإنتاج، وعناوين التشغيل تُستثنى من أي مسح (`node scripts/attack-surface.js ... --ot-exclusions <ملف من GET /api/ot-safety>`).
- لا يُنفذ أي إجراء استجابة على جهاز تشغيل دون موافقة سلامة منفصلة (`POST /api/ot-safety/approvals`) من معتمد سلامة يعيّنه المسؤول، ليس هو الطالب ولا المعتمد، مع وجود المشغل في الموقع وبديل يدوي وحالة عملية آمنة. والإجراءات المعطلة على أنظمة السلامة مرفوضة دائمًا. الإرشادات مبنية على NIST SP 800-82 Rev. 3.

## التحقق من المسار قبل العزل (CG-101)

- من كل محول وصول (أوامر قراءة فقط): `node scripts/port-map.js --switch-ref <محول> --authorization-ref <مرجع> --output out.json --mac-table <show mac address-table> --switchport <show interfaces switchport> --arp <show ip arp> --lldp <show lldp neighbors detail>`.
- يتحقق CyberGuard من المسار IP ← MAC ← منفذ المحول ← VLAN ← المستخدم (من سجلات NAC) ← الأصل، ويرفض العزل إذا كان العنوان يرتبط بعدة عناوين MAC، أو المنفذ trunk أو صاعدًا لمحول/موجه، أو يخدم مضيفًا افتراضيًا أو عدة أجهزة، أو VLAN لا تطابق.
- إيقاف منفذ محول أو عزل NAC لا يُقبل إلا بعد هذا التحقق، ويظهر المسار في نافذة تفاصيل الأصل.

## حماية مستوى الإدارة (CG-102)

- سياسة `management.policy` تحدد الأجهزة المشمولة، والمضيفات الوسيطة أو شبكات الإدارة المعتمدة، والبروتوكولات المعتمدة (ssh/https/snmpv3/...)، واشتراط مرجع تغيير، وساعات الإدارة.
- كل جلسة إدارية موثقة (`remote.authenticated`) على جهاز مشمول تُفحص: مصدر غير معتمد أو بروتوكول غير معتمد أو بلا مرجع أو خارج الساعات دون مرجع طارئ ترفع CG-MGMT-ACCESS-102. وتُعرض الأجهزة التي ما زالت تفعّل Telnet أو HTTP أو SNMPv1/v2c.

## طبقة توحيد OCSF (CG-103)

- `GET /api/ocsf/export?hours=24` يصدّر السجلات الموحدة كفئات OCSF 1.3.0 (Authentication، Network Activity، HTTP Activity، DNS Activity، DHCP Activity، Detection Finding، API Activity، أو Base Event) مع إصدار المخطط والصيغة الأصلية والمصدر في metadata.
- لكل صيغة يُعرض في صفحة سجل الأحداث: الحقول التي تحتاجها الفئة ولا يوفرها المصدر، وعدد السجلات التي تغيّر معناها (مثل اختلاف مقياس الخطورة أو حذف مسار الرابط للخصوصية).

## تغطية الكشف السحابي (CG-104)

- صفحة السحابة تعرض لكل مزود (AWS وAzure وGoogle Cloud) ولكل مجال (الهوية، الحوسبة، التخزين، المفاتيح، الشبكة، السجلات) هل وصل سجل التدقيق وملاحظات التهديد وسجلات التدفق خلال 30 يومًا، وكم قاعدة وملاحظة تغطيه: مغطى، أو مستوى التحكم فقط (التخزين يحتاج سجلات البيانات)، أو مرئي بلا قواعد، أو غير مرئي.
- إذا كانت حسابات مزود مجرودة ولم يصل سجل تدقيقها خلال 30 يومًا تُرفع CG-CLOUD-COVERAGE-104.

## أمان Kubernetes والحاويات (CG-105)

- سجل التدقيق: `node scripts/k8s-to-telemetry.js audit --input audit.jsonl --cluster-ref <عنقود> --output out.json` يرفع CG-K8S-AUDIT-105 على فتح طرفية في الحاويات، وقراءة الأسرار من غير مكونات النظام، ومنح cluster-admin، والأحمال المميزة (privileged/hostPID/hostNetwork)، والوصول المجهول المسموح. لا تُنسخ أجسام الطلبات.
- RBAC وPod Security Admission: `rbac --clusterrolebindings <kubectl get clusterrolebindings -o json> --clusterroles ... --namespaces ...` (CG-K8S-RBAC-105).
- صور الحاويات: `trivy --input <trivy image -f json>` يرفع CG-CONTAINER-VULN-105 للثغرات الحرجة التي لها إصلاح. وتنبيهات Falco تأتي بصيغة falco-json. ودعم EKS/AKS/GKE المُدار مرحلة لاحقة.

## سلسلة توريد البرمجيات (CG-106)

- SBOM: `node scripts/supply-chain.js sbom --input sbom.json --osv osv.json --project <اسم> --output out.json` يقرأ CycloneDX أو SPDX ويطابق التبعيات مع نشرات OSV (يرفع CG-SUPPLY-106 لما له إصلاح) ويعد المكونات بلا معرف حزمة أو بصمة أو ترخيص.
- CI/CD: `ci --repo <مسار>` يكشف الإجراءات الخارجية غير المثبتة على بصمة، وpull_request_target الذي يجلب شيفرة غير موثوقة، وصلاحيات الرمز الواسعة أو غير المقيدة، وطباعة الأسرار، والأسرار المحفوظة في المستودع (دون تخزين قيمتها). مستودع CyberGuard نفسه نظيف.
- البرامج المنشورة: `verify --artifact <ملف> --checksums SHA256SUMS --signature <توقيع> --public-key <مفتاح> --provenance <SLSA> --trusted-builder <id>`.

## أمان واجهات API والويب (CG-107)

- `node scripts/web-check.js scan --scope web-scope.json --output web.json`: يفحص فقط العناوين المدرجة في نطاق مصرح به (مرجع التفويض، المالك، نهاية النافذة، البيئة).
- يكشف: CORS الذي يعكس أي أصل (مع بيانات الاعتماد = مرتفع)، نقاطًا تجيب دون المصادقة المطلوبة، مفاتيح API في الرابط، غياب تحديد المعدل (طلبات متكررة فقط في بيئة test أو staging)، وترويسات الأمان وخصائص ملفات تعريف الارتباط وكشف إصدار الخادم. لا تُحفظ معاملات الاستعلام.
- أحداث WAF (ModSecurity وAWS WAF وCloud Armor) تُلخص في صفحة الثغرات. التطبيق نفسه (CyberGuard) اجتاز هذا الفحص.

## إجابات مستندة إلى الأدلة (CG-122)

- كل شرح من `/api/ai-analysis/<id>` يلتقط نسخة مؤرخة ببصمة SHA-256 من كل مصدر يستشهد به (الحدث المخزن، القاعدة، التنبيه، الأصل، النشرة، خطة الاستجابة)، وتُعاد النسخة نفسها إذا لم يتغير المصدر. الإجابة تُحفظ دون تغيير ويمكن فتحها لاحقًا من `/api/ai-answers/<id>` مع التحقق من سلامتها وسلامة نسخها.
- الإخفاء حسب الدور: الأسرار (مفاتيح AWS، الرموز، كلمات المرور، المفاتيح الخاصة) مخفية للجميع دائمًا؛ المشاهد لا يرى الحسابات والبريد والعناوين الداخلية والجوال والهوية؛ المحلل يرى الحسابات والعناوين مع إخفاء جزئي للبريد وإخفاء الجوال والهوية؛ المدير يرى الجوال والهوية مقنعة جزئيًا. البصمات والمعرفات لا تُخفى.
- لكل ادعاء درجة عدم يقين وأسبابها: دليل مفقود، دليل قديم (أكثر من 7 أيام)، مصدر صامت أو ملغى، مصدر واحد، أو ادعاء بلا سجل دليل.

## الحماية من حقن التعليمات (CG-121)

- السجلات والبريد والتذاكر ونتائج البحث بيانات غير موثوقة دائمًا. قبل التحليل تُفحص كل نصوص الدليل بحثًا عن تعليمات موجهة للذكاء الاصطناعي (تجاهل التعليمات، تغيير الدور، طلب تنفيذ أو موافقة، أوامر shell، روابط تسريب، علامات أدوار، وأحرف مخفية أو معكوسة الاتجاه) بالعربية والإنجليزية.
- لا يصل النص إلى أي نموذج إلا داخل كتلة بيانات موسومة بالمصدر والبصمة وحد عشوائي لكل طلب، منفصلة عن سياسة النظام الثابتة (بصمتها في `/api/ai-guard`).
- الدليل الذي يحوي تعليمات يرفع CG-AI-INJECTION-121، وتُحجب الاقتراحات المأخوذة منه. يُرفض أي مقترح يظهر هدفه فقط في نص يوجه التعليمات أو يحمل مبرره تعليمات، وتُرفض إجابة النموذج السحابي التي تحمل تعليمات أو أوامر. كل رفض يُسجل.
- `POST /api/ai-guard/scan` يفحص نصوص الموصلات ويعيدها كبيانات غير موثوقة منظفة.

## خطط استجابة متعددة المزودين (CG-120)

- الخطة سلسلة نوايا (عزل الجهاز، حظر العنوان، تعطيل مفتاح السحابة)، لا نص أوامر. لكل خطوة يُختار المزود حسب الهدف والموصل المتاح فعلًا: وكيل الجهاز (Windows/Linux)، أو AWS/Azure/Google Cloud لآلة سحابية موجودة في جرد السحابة، أو Cisco ISE، أو منفذ محول Cisco/Huawei متحقق عبر خريطة المنافذ. `POST /api/orchestrations/plan` يعرض الاختيار وسبب رفض كل بديل.
- الخطط: احتواء جهاز، احتواء جهاز وحظر عنوان القيادة والتحكم (الخطوتان مطلوبتان)، احتواء بيانات اعتماد سحابية.
- `POST /api/orchestrations` يبدأ التشغيل، وتكرار الطلب نفسه يعيد التشغيل المفتوح نفسه دون إجراءات مكررة. كل خطوة إجراء محكوم (معاينة وموافقة مستقلة ومستوى الأمان).
- `POST /api/orchestrations/<id>/advance` يتقدم حسب حالة الإجراءات: الخطوة الفاشلة تُعاد حتى ثلاث محاولات (كل محاولة تحتاج موافقة جديدة)، وإذا فشلت خطوة مطلوبة يُتراجع عن الخطوات المكتملة بترتيب عكسي واحدة بعد الأخرى بعد التحقق من كل تراجع.
- أُضيفت إجراءات سحابية مقيدة: `cloud.isolate-instance` و`cloud.disable-access-key` وعكسهما عبر موصل سحابي.

## مستويات أمان الاستجابة (CG-119)

- **قراءة فقط**: المعاينة والفحص المسبق والصيد والتقارير؛ لا تغيير ولا موافقة.
- **استجابة منخفضة التأثير** (حظر أو سماح عنوان أو منفذ أو تطبيق أو نطاق، فك الحجر، تغيير سجل الأصل): موافق مستقل واحد.
- **تغيير حساس** (عزل جهاز، حجر NAC، إطفاء منفذ، إيقاف أو تعطيل خدمة، حجر ملف): موافق مستقل، ثم تأكيد منفصل يكتب فيه المنفذ اسم الهدف (صالح 10 دقائق ويجب أن ينفذ الشخص نفسه)، ونافذة تغيير فعالة للأصل أو طوارئ معلنة بمرجع حادث وسبب.
- **إجراء مدمر** (إطفاء الجهاز، إزالة أو تغيير خدمة دائم): موافق مستقل وموافق سلامة ثالث، والتأكيد المكتوب، ونافذة تغيير فعالة دون أي استثناء طوارئ.
- `POST /api/change-windows` يضيف نافذة (حتى 24 ساعة) لأصل أو للكل، و`POST /api/actions/<id>/confirm` للتأكيد، و`GET /api/actions/<id>/safety-status` يبين الناقص.

## التحقق من نتيجة الإجراءات (CG-118)

- تقرير الموصل بنجاح الإجراء ليس دليلًا كافيًا. يُعد الإجراء «متحققًا بشكل مستقل» فقط بوجود حدث `response.outcome_check` من مصدر غير الموصل المنفذ (فحص اتصال، حالة خدمة أو تشغيل، جلسة NAC...) يطابق الحالة المتوقعة، والموصل نفسه لا يستطيع إرسال هذا الفحص.
- يصبح الإجراء «غير فعال» إذا ناقضه فحص مستقل أو ظهرت في سجلات التدفق حركة كان يجب أن يوقفها بعد تطبيقه، ويرفع ذلك CG-CONTROL-INEFFECTIVE-118.
- تُعرض مدة التطبيق من وقت التحقق حتى التراجع الموثق، ويظهر خطأ التنفيذ كما أبلغه الموصل.
- فشل التراجع يُسجل بحالة `rollback-failed` (والإجراء ما زال مطبقًا) ويرفع CG-ROLLBACK-FAILED-118 الحرج، ويمكن إعادة محاولة التراجع.

## الفحص المسبق قبل الاستجابة (CG-117)

- `POST /api/response-preflight` مع `{"identifiers":{"ip","mac","hostname","cloud_id","asset_id"},"action_type"}` يعطي تقريرًا للقراءة فقط قبل أي إجراء.
- تحديد الهدف: يُجمع الجهاز الذي تراه عدة مصادر في هدف واحد، ويُمنع الإجراء إذا طابقت المعرفات عدة أجهزة أو أشارت إلى أجهزة مختلفة أو لم تطابق شيئًا.
- الأثر: الأهمية والخدمة والمالك ونوافذ الصيانة، والأجهزة التي تتصل به خلال 7 أيام (مع حركة DNS والدليل)، والدور المحمي مثل وحدة التحكم بالمجال، ومسار العزل عبر المحول.
- الموصل والقدرة المرخصة (الإصدار والترخيص من فحص قدرات الجهاز)، وحالة قناة الإدارة (أثرها وعمر الفحص أقل من 15 دقيقة)، وتبعيات الخدمات.
- كل فحص: سليم أو تنبيه أو يمنع. النتيجة الجاهزة تحتاج بعدها المعاينة المحكومة وموافقة مسؤول آخر.

## منصة الصيد (CG-116)

- صفحة الأحداث فيها «منصة الصيد»: استعلام زمني (حتى 90 يومًا) على الأدلة المخزنة عن الحسابات أو العمليات أو الاتصالات أو التنقل بين الأجهزة أو التغييرات، مع مرشحات الحساب والجهاز والعنوان والمنفذ والنص. لا يُقبل SQL حر.
- `POST /api/hunts/run` يعيد الصفوف مرتبة زمنيًا مع خط زمني بالساعة وأكثر الأجهزة والحسابات والعناوين وبصمة SHA-256 للنتيجة.
- `POST /api/hunts` يحفظ الصيد مع فرضيته، و`/api/hunts/<id>/notes` يضيف ملاحظة مرتبطة بأحداث، و`/api/hunts/<id>/reports` يجمّد النتيجة والملاحظات والاستنتاج في تقرير. الملاحظات والتقارير لا تُعدّل.

## مختبر التحقق من الكشف (CG-115)

- سيناريوهات اختبار آمنة: بيانات اصطناعية بعناوين توثيق، لا يُنفذ أي أمر على أي جهاز ولا يخرج شيء من العملية. تُشغَّل في نسخة CyberGuard معزولة في الذاكرة بالقواعد الحالية، ولا يصل منها حدث أو تنبيه إلى بيانات الإنتاج.
- السيناريوهات: تخمين RDP، انتشار SMB، RDP مكشوف، نفق DNS، قاعدة تسمح بالكل، تغيير نظير VPN، مستند ماكرو، منفذ وصول عن بعد، ونشاط سليم لقياس الإنذارات الكاذبة.
- `POST /api/validation-lab/run` مع `{"scenario_id":"all"}` أو معرف سيناريو، و`POST /api/validation-lab/replay` مع `{"source_id":...,"since":...,"until":...}` يعيد تشغيل الأحداث المخزنة بالقواعد الحالية ويقارنها بما أطلقه الإنتاج لها.
- أي كشف متوقع لم يعمل يرفع CG-VALIDATION-MISS-115؛ سجل التشغيلات لا يُعدّل.

## خزنة الأدلة وسلسلة الحيازة (CG-114)

- يُرفق الدليل الأصلي بالحالة كما هو: `POST /api/cases/<id>/evidence?name=&source_ref=&acquisition=&collected_at=&expected_sha256=` بمحتوى `application/octet-stream` (حتى 50 ميجابايت). يُحفظ باسم بصمته SHA-256 للقراءة فقط مع وقت جمعه ومصدره وطريقة الجمع والجامع، ويُرفض إذا خالف البصمة المعلنة من المصدر.
- الدليل لا يُعدّل أبدًا: النسخة المنقحة أو المستخرجة عنصر جديد مرتبط بالأصل مع وصف التحويل (`/api/evidence/<id>/derive`).
- قراءة المحتوى (`/api/evidence/<id>/content`) تتطلب ذكر الغرض وتُسجل باسم المستخدم. كل جمع واطلاع وتصدير وتحقق يُضاف لسلسلة بصمات خاصة بالعنصر وللسجل العام.
- قاعدة البيانات ترفض تعديل أو حذف الأدلة وسجلات الحيازة وتعديل الأحداث المخزنة. `/api/evidence-integrity` يعيد حساب بصمات الأدلة والأحداث وسلسلة التدقيق ويرفع CG-EVIDENCE-TAMPER-114 عند أي اختلاف.
- `/api/evidence/<id>/custody-export` يصدّر حزمة الحيازة موقعة بمفتاح Ed25519 الخاص بالتثبيت.

## خريطة ATT&CK وD3FEND (CG-110)

- كل قاعدة تنبيه في CyberGuard (`lib/attack-mapping.js`) مربوطة بتقنيات MITRE ATT&CK والتكتيك، والحساس ونوع الدليل، والحدث الدال، والتحليل، وتقنيات MITRE D3FEND للكشف والاستجابة، والاختبار الآلي الذي يثبت أنها تعمل.
- اختبار `tests/attack-mapping.test.js` يفشل إذا أُضيفت قاعدة جديدة بلا ربط أو أشار الربط إلى اختبار غير موجود.
- صفحة التهديدات تعرض لكل قاعدة هل بيانات الحساس تصل فعلًا وكم تنبيهًا أطلقت. `/api/attack-mapping/navigator-layer` يصدّر طبقة ATT&CK Navigator (الإصدار 4.5) لعرض التغطية في أداة MITRE.

## أمن البيانات ومنع تسربها (CG-109)

- يُعلن كل مخزن بيانات بحدث `data.store`: التصنيف (عام/داخلي/سري/مقيد)، المالك، الموقع، التشفير، الإتاحة العامة، وجود بيانات شخصية، الأساس القانوني، ومدة الاحتفاظ.
- يكشف CyberGuard المخازن الحساسة المتاحة للعامة أو غير المشفرة أو خارج المناطق المسموحة (`/api/data-security?allowed_regions=sa-central`) ويرفع CG-DATA-109.
- يقيس حجم الخروج إلى الإنترنت لكل جهاز من سجلات التدفق مقارنة بمعدله اليومي المعتاد، ويرفع CG-DATA-EGRESS-109 عند تجاوز 5 أضعاف و500 ميجابايت خلال 24 ساعة.
- لا يُفحص محتوى الملفات. فحص المحتوى يحتاج موافقة مسجلة فيها مرجع قانوني ومراجع خصوصية ونطاق محدد، وإلا يُرفض الحدث.

## أمان البريد والتصيد (CG-108)

- `node scripts/email-security.js domain --domain <نطاق> --selectors selector1,selector2`: يقرأ SPF وDMARC وDKIM من DNS ويكشف +all و?all وكثرة الاستعلامات وp=none وغياب التقارير أو DKIM.
- `eml --input رسالة.eml --internal-domains <نطاقاتنا>`: يحلل نتائج المصادقة وتعارض Reply-To وانتحال اسم العرض وpunycode والمرفقات الخطرة (امتدادات تنفيذية أو مزدوجة) والروابط المضللة وروابط IP. لا يُخزن نص الرسالة أو موضوعها.
- `audit --input <سجل تدقيق Microsoft 365>`: يكشف قواعد التحويل وإعادة التوجيه خارج المؤسسة والقواعد التي تخفي الرسائل. كلها ترفع CG-EMAIL-108.
